# Finding your way around PIXIWYG

This is a guide, not a rulebook. It covers how the repository is laid out, how a change in `src/` reaches the page,
where to look for whatever you want to change, and how the code is commented. Read the [README](README.md) first for
what PIXIWYG is and how to run it.

## How a change reaches the page

PIXIWYG ships as one file, `index.html`, with one `<style>`, one block of markup and one inline `<script>`. It is
written as many small files in `src/`, and `tools/scripts/build.mjs` stitches them together:

```
src/template.html     the document around everything (head, CSP, fonts) with three injection points
src/build.json        three ordered lists of files under src/: styles, markup, scripts
src/<feature>/…       the files those lists name
        │
        ▼  npm run build (or npm run watch, which rebuilds on every save)
index.html            the app, with its Content-Security-Policy stamped to the new script's hash
```

The usual loop: `cd tools`, run `npm run watch` in one terminal and `npm run serve` in another, edit a file in
`src/`, then reload http://localhost:4173/. `npm test` rebuilds the page before it runs. `index.html` is committed
because it is the hostable app, so commit the rebuilt page together with your source change.

Some things about `build.json` that are easy to miss:

- **Scripts** are listed in load order. They all share one scope, so a function in `paint/filters.js` can call one in
  `page/render.js` directly, with no imports. That's also why the order matters: a top-level `const` has to come
  before anything that runs at load time and reads it. Top-level names must be unique across all scripts, and the
  build stops and names both files if two clash (`tools/scripts/globals.mjs`).
- **Styles** cascade in list order. When two rules of equal specificity conflict, the one in the later file wins.
- **Markup** is listed in DOM order, which is also tab order, and stacking order when z-indexes tie. A side panel's
  panes live with their features and are pulled in by `<!-- INCLUDE: catalog/cards.html -->` lines in
  `app/panels.html`.
- A new file only reaches the page once it's in `build.json`.

## Where things are

Each folder under `src/` is one feature. Files that share a base name belong together: `app/settings.js`,
`app/settings.css`, `app/settings.html` and `app/settings.spec.mjs` are the settings page's behaviour, look, markup
and tests.

| Folder | The feature |
| --- | --- |
| `app/` | The frame around everything: boot, the toolbar, side panels and docking, workspaces, the command palette, keyboard shortcuts, settings, interface themes (`app/themes/*.css`), the title screen, first visit and tours, about and problem reports. `app/start.js` opens the script, holds the comment-tag legend and the version; `app/boot.js` closes it, starts the app and defines the `window.__pixiwyg` test hook. `app/state.js` is the one state object every feature shares |
| `page/` | The page being edited: element kinds, rendering, the stage, pointer, snapping, text editing, tables and lists, the Inspector, the project tree and contexts, symbols, groups, Boxes, autoformat, canvas types, responsive mode, background, site pages, accessibility checks |
| `catalog/` | The Add panel: the stylesheet library, catalog cards and their thumbnails, primitives and the parts kit |
| `styles/` | Stylesheets themselves: selector parsing, compiling, baking imports, sample sheets, the page palette and color carry-through, style graphs, opening a rule as nodes, style sets, text effects |
| `paint/` | Paint Studio: layers, the palettes that dock around the canvas, zoom, tools and brushes, filters (WebGL), selection, transforms, blending, frames, GIF export |
| `music/` | Sequencer: songs, MIDI, the synth, SoundFonts, samples and effects, note input, playback, the Webamp player |
| `logic/` | Page logic and animation: the runtime, Play mode, the node editor, checks and suggested interactions, the animation editor, the timeline, the example calculator |
| `writing/` | Manuscripts, Markdown import, the page view, the Text panel, the Write workspace |
| `3d/` | 3D models: parsers, building from shapes (`3d/modeler.js`, with csg.js for cuts and earcut for 3D text; handles, groups, STL export), baking to atlases, the page element, the workspace panel, model primitives, drag to turn |
| `project/` | A project as a file: saving and opening, browser storage, versions, undo, export, print, live preview, references, autopublish, magnet links, the project lock, the starter project |

Outside `src/`:

| Path | What it's for |
| --- | --- |
| `lib/` | Vendored third-party files, left exactly as upstream ships them (a script may be wrapped to expose one global, as `gifenc.js` and `csg.js` are). Add a library's license to `lib/NOTICES.txt` |
| `examples/` | Example projects, generated by `tools/scripts/build-examples.mjs` (`npm run examples`) |
| `tauri/` | The desktop shell in Rust: the `app://` origin, window and download handling, the Wayland/X11 choice. `cargo test` covers it |
| `tools/` | `package.json` and every script: build, dev server, CSP stamp, versions, installers, local install. `tools/tests/` holds the repository-wide specs and `helpers.mjs` |
| `docs/` | `UX_UI.md`, the standard UI work is checked against; `notes.md`; `research/` |

### If you want to change…

| …this | start here |
| --- | --- |
| a toolbar button or what a workspace shows | `app/toolbar.html`, `app/toolbar.css`; overflow into More is `app/toolbar-fit.js` |
| a command in the palette | `CMD_ITEMS` in `app/command-palette.js` |
| a keyboard shortcut | `app/keyboard.js`; the shortcuts window is `app/keys-window.*` |
| the app's colors or type | the tokens in `app/base.css`; built-in themes in `app/themes/`, starting from `app/themes/template.css` |
| a tour or the welcome | `app/tour.js`, `app/welcome.*` |
| an element kind (what it is, how it edits) | `TAGS` in `page/elements.js`, rendering in `page/render.js` |
| the Inspector | `page/inspector.*` |
| how dragging, snapping or resizing feels | `page/pointer.js`, `page/snapping.js` |
| what's saved in a project file | `packProject` and `readProject` in `project/projects.js` |
| what an export contains | `buildExport` in `project/export.js` |
| a paint filter | `paint/filters.js` (the shaders and the catalogue), its panel in `paint/filter-panel.js` |
| Paint layers, their effects, or where its palettes go | `paint/layers.*`, `paint/layer-fx.js`, `paint/palettes.*` |
| how a brush paints, or the built-in brushes | `paint/brush-engine.js`; the palette and editor are `paint/brush-library.*` and `paint/brush-editor.*` |
| a node kind in page logic | `logic/runtime.js` (what it does) and `logic/editor.js` (how it's drawn) |
| a style graph node | `styles/graphs.js` |
| a sequencer effect | `music/effects.js` |

When the table runs out, search for the section:

```sh
grep -rn "// SECTION:" src            # every script section, with its file
grep -rln "pgwb" src                  # every file that names a class
grep -rn "RULE:" src/paint            # the product rules one feature holds to
```

Any file is named in the bundled page too: `grep -n "// SECTION:" index.html` reads as the app's table of contents.

## Tests

A feature's specs sit in its folder, next to its code: `src/paint/paint.spec.mjs`, `src/music/player.spec.mjs`, and
so on. Specs that check the whole repository live in `tools/tests/`: security, accessibility against
`docs/UX_UI.md`, comment conventions, and the benchmark. All of them drive the real page in Chromium through
Playwright, and share `tools/tests/helpers.mjs` (`boot`, `ws`, `tb`, `freshPage`…).

```sh
cd tools
npm test                                    # everything
npx playwright test ../src/paint            # one feature
npx playwright test -g "groups"             # tests whose title matches
npm run test:tauri                          # the desktop shell
```

Test titles state the behaviour they hold, so a failing title reads as the thing that broke. Many start with a tag,
`RULE:`, `FIX:`, `PERF:` and so on, when the test guards that kind of thing.

## How the code is commented

Comments say *why*: a constraint, an invariant, an engine limit, the bug a line keeps away. Code that needs a comment
to say *what* it does is usually better rewritten. Every comment starts with a tag in capitals and a colon, so one
search finds every comment of a kind:

| Tag | Use |
| --- | --- |
| `SECTION:` | the start of a file or of a part of one; `grep '// SECTION:'` is the table of contents |
| `INVARIANT:` | something the code relies on; break it and something else breaks |
| `SAFETY:` | untrusted input, sanitizing, privilege, resource limits |
| `PERF:` | why code is shaped for speed or memory, with the measured numbers |
| `HACK:` | an upstream or engine workaround, or a deliberate clever trick |
| `FIX:` | why a non-obvious line exists: the bug it keeps from coming back |
| `COMPAT:` | old data, other browsers, other platforms |
| `FORMAT:` | file formats, data shapes, protocols |
| `RULE:` | product behaviour enforced on purpose; changing it is a design decision |
| `TODO:` | a known gap |

A comment that runs onto more lines indents its continuation lines by three spaces, so they read as one comment:

```js
// RULE: a theme is a .css file that sets the tokens below under :root[data-apptheme]. Light and dark stay built in;
//   a loaded theme becomes one more stop on the Theme button.
```

The same tags work in every language here: `/* RULE: … */` in CSS, `# FORMAT: …` in shell and YAML, `// SAFETY: …`
in Rust. HTML files open with an `<!-- SECTION: … -->` line naming what they hold, and the build leaves those out of
the page. Theme files also carry build directives, `/* INCLUDE: … */` and `/* ASSET: … */`, that pull fonts and
images out of `lib/` (described in `build.mjs`).

`tools/tests/conventions.spec.mjs` walks every source file and lists any whole-line comment without a tag, so a
missed one shows up in `npm test`. Vendored files in `lib/` keep their upstream comments and license headers.

## Changing the UI

UI changes are measured against [docs/UX_UI.md](docs/UX_UI.md): actions where hands and eyes already are, no
duplicate paths, few clicks for common things, powerful tools in reach, uniform controls, semantic tokens rather than
raw colors, never color alone, full keyboard support, and contrast that holds. `tools/tests/a11y.spec.mjs` checks the
parts of it a test can see.
